처음 GitHub에 올리는 순간부터
Web App의 Version 관리가 시작된다

앞 단계에서 내 컴퓨터에서 App이 정상 동작하는 것을 확인했습니다. 이제 처음 완성본을 GitHub에 올리고, 이후 수정할 때마다 Commit(변경 상태 기록) → Push(GitHub로 전송) → 필요하면 Deploy/Publish(배포: Internet에서 실제로 볼 수 있게 반영) → 실제 URL 확인 과정을 반복합니다. 내 컴퓨터에서는 정상이어도 실제 배포 환경에서만 발견되는 문제가 있기 때문에, 수정본을 다시 올려 Internet에서 확인하는 일이 계속 생깁니다. Git의 강점은 이때마다 변경 이력이 남아 “지금 Version보다 이전 Version이 더 좋았다”면 과거 상태를 찾아 비교하거나 되돌릴 수 있다는 것입니다.

00

GitHub를 왜 많이 사용할까? — 저장소이자 “개발의 역사”를 남기는 곳

GIT = VERSION HISTORY · GITHUB = ONLINE DEVELOPMENT PLATFORM

GitHub를 단순히 “파일을 올려 두는 곳”으로만 생각하면 중요한 장점을 놓치게 됩니다. 하나의 Web App도 처음 완성한 뒤 Internet에 배포해 보면 고칠 부분이 계속 생깁니다. 그래서 수정 → 기록 → GitHub에 올리기 → 배포 → 실제 URL 확인을 여러 번 반복하게 됩니다. 이때 Git은 매번 달라진 내용을 Commit(커밋: 그 시점의 변경 상태를 기록하는 것)으로 남기고, GitHub는 그 기록을 Repository(리포지토리: 프로젝트 파일과 변경 이력을 함께 보관하는 온라인 저장소)에 차곡차곡 쌓아 둡니다. 덕분에 “이번 수정이 전보다 별로네”라고 느끼면 이전 기록을 찾아 비교하거나 되돌아갈 수 있습니다.

① 최초 완성내 PC에서 Test
② Commit현재 상태 기록
③ PushGitHub에 전송
④ Deploy / PublishInternet에 배포
⑤ 실제 URL Test배포 환경에서 확인
⑥ 수정 후 반복새 Commit으로 역사 추가
Version 번호를 꼭 매번 직접 붙여야 할까?
꼭 그렇지는 않습니다. Git에서는 각 Commit 자체가 하나의 Version 기록입니다. 중요한 완성 시점에만 v1.0, v1.1처럼 Tag/Release(태그/릴리스: 사람이 알아보기 쉬운 Version 이름표)를 붙일 수 있습니다. 즉, Git의 핵심은 파일 이름을 계속 최종1, 최종2, 진짜최종3으로 만드는 것이 아니라 하나의 프로젝트 안에 변경 역사를 체계적으로 남기는 것입니다.

GitHub와 Microsoft는 어떤 관계이고, Google·Microsoft·AWS는 왜 비슷한 서비스를 만들까?

GitHub는 2008년에 시작된 개발 협업 플랫폼이고, Microsoft가 2018년에 GitHub를 인수했습니다. 그렇다고 GitHub가 Microsoft 제품만 올리는 곳이 된 것은 아닙니다. 지금도 여러 회사의 기술과 다양한 언어로 만든 프로젝트를 저장하고 협업하는 개방형 개발 플랫폼으로 쓰입니다.

여기서 더 큰 그림을 보면 이해가 쉽습니다. Google, Microsoft, Amazon(AWS) 같은 회사들은 모두 “우리가 만든 Web App을 Internet에서 실제로 실행하고 보여주려면 무엇이 필요할까?”라는 같은 문제를 해결하기 위해 각자 비슷한 Cloud 서비스를 제공합니다. 예를 들어 Google Cloud에는 Cloud Run·Firebase Hosting, Microsoft Azure에는 App Service·Static Web Apps, AWS에는 여러 Application Hosting(앱 호스팅: Web App을 Internet에서 실행해 주는 서비스) 방법이 있습니다.

회사와 제품 이름은 달라도 저장 → Build(빌드: 실행 가능한 형태로 준비) → Deploy/Publish(배포: Internet에서 접속할 수 있게 공개) → 운영 이라는 기본 목적은 비슷합니다. 그래서 우리는 Google AI Studio만 “정답”으로 외우는 것이 아니라, Web App을 세상에 보여주려면 이런 종류의 배포 서비스가 필요하고, 회사마다 비슷한 서비스를 경쟁적으로 제공한다는 큰 구조를 이해하면 됩니다. 이번 수업에서는 그중 Google AI Studio를 경험해 보는 것입니다.

GitHub에 쌓인 공개 Code는 오늘의 AI Coding과 어떤 관계가 있을까?

GitHub에는 Public Repository(공개 저장소: 누구나 내용을 볼 수 있는 프로젝트 공간)가 아주 많이 있습니다. 개발자들은 이곳에서 다른 사람이 만든 Code를 구경하고, 좋은 방법을 배우고, 함께 문제를 고쳐 왔습니다. 마치 전 세계 사람들이 수십 년 동안 “내가 푼 문제와 풀이 방법”을 거대한 온라인 도서관에 쌓아 온 것과 비슷합니다.

그중에는 Open Source Code(오픈소스 코드: 정해진 사용 조건에 따라 다른 사람이 보고·수정·재사용할 수 있도록 공개한 코드)도 많습니다. 이런 공개 Code와 설명 자료들은 사람에게도 좋은 교과서가 되었고, Code를 이해하고 만들어 주는 AI가 발전하는 데에도 중요한 학습 자료 중 하나가 되었습니다. GitHub도 Copilot(코파일럿: GitHub의 AI 코딩 도우미)에 사용되는 기반 모델이 공개적으로 이용 가능한 Text와 Code를 학습에 활용했다고 설명합니다.

그래서 오늘 우리가 “이런 기능을 만들어 줘”라고 말하면 AI가 Code를 만들어 주는 세상은 어느 날 갑자기 생긴 것이 아닙니다. 수많은 개발자가 Code를 공유해 온 문화 + Open Source(오픈소스: 함께 보고 발전시킬 수 있도록 공개하는 개발 문화) + 강력한 AI 모델 + Cloud 서비스 + 편리한 개발도구가 오랫동안 함께 발전하면서 지금의 Vibe Coding으로 이어졌다고 이해하면 충분합니다.

Repository
리포지토리 · 프로젝트 저장소

한 프로젝트의 파일과 변경 기록을 함께 보관하는 공간입니다.

📁 비유: Web App 하나를 위한 전용 서랍
Commit
커밋 · 변경 상태 기록

현재 파일 상태를 하나의 기록 시점으로 남깁니다.

📸 비유: “여기까지 정상”이라는 사진을 찍는 것
Push
푸시 · GitHub로 전송

내 PC에 기록된 Commit을 원격 GitHub Repository로 보냅니다.

📤 비유: 내 작업일지를 온라인 창고에 업로드
Tag / Release
태그 / 릴리스 · 중요한 Version 이름표

예: v1.0, v1.1. 모든 Commit에 붙이는 것은 아니며 중요한 배포 시점을 표시할 때 사용합니다.

🏷️ 비유: 수많은 작업 사진 중 “첫 공식판”에 라벨 붙이기
Push
푸시 · GitHub 저장소로 보내기

내 컴퓨터의 Code와 Commit(변경 기록)을 GitHub로 보내는 것. 아직 Internet에 Web App을 공개하는 배포는 아닙니다.

Deploy
디플로이 · 배포(Internet에서 실행되게 반영)

Code를 실제 실행 환경에 반영하여 Web에서 동작하게 하는 과정.

Publish
퍼블리시 · 게시/공개(사용자가 접속할 수 있게 공개)

서비스에서 배포·공개 버튼 이름으로 자주 사용. Google AI Studio에서는 Publish라고 부름.

Republish
리퍼블리시 · 재배포

수정한 새 Version을 다시 공개 환경에 반영하는 것.

처음 보는 영어가 나와도 겁낼 필요가 없습니다.
이 수업에서는 Push = GitHub에 저장, Deploy/Publish = Internet에서 볼 수 있게 배포, Republish = 수정본을 다시 배포 정도만 구분하면 충분합니다.
다음 단계 연결: GitHub에 최종 Source와 Version 기록을 저장한 뒤, 다음 수업에서는 Google AI Studio로 가져가 Publish(배포: Internet에서 실제로 접속할 수 있게 공개)하는 과정을 진행합니다.
01

GitHub에 올리기 전에 먼저 보호해야 할 것을 확인한다

PUBLICATION PREFLIGHT · PROTECT BEFORE PUSH

초보 학생이 “어떤 파일은 올리고 어떤 파일은 빼야 하지?”를 모두 판단하기는 어렵습니다. 그래서 학생이 파일을 하나씩 고르는 것이 아니라, 보호해야 할 정보의 종류만 이해하고 → 토비가 안전 점검 Prompt(프롬프트: AI에게 주는 작업 지시문)를 만들고 → 지니가 실제 검사를 수행하도록 합니다.

Public Preflight

공개 전 안전점검. GitHub에 올리기 전에 비밀정보나 불필요한 파일이 섞이지 않았는지 확인하는 단계

Secret

비밀정보. API Key(서비스 이용 열쇠), Token(접근 권한표), Password(비밀번호)처럼 공개되면 안 되는 정보

.gitignore

Git에게 “이 파일은 기록하거나 올리지 마”라고 알려주는 제외 목록 파일

1
학생 · 공개 승인 전 멈춤

“GitHub에 올릴 준비를 해줘. 아직 Push하지 마.”라고 요청합니다.

2
토비 · Public Preflight Prompt 작성

Secret·개인정보·내부 작업기록을 제외하고 공개에 필요한 파일만 남기도록 지니에게 줄 지시문을 만듭니다.

3
지니 · 실제 파일 검사

.gitignore, Secret Scan(비밀정보 검사), 공개 파일 목록, Repository Root(저장소의 가장 바깥 시작 폴더)를 확인하고 결과를 보고합니다.

4
학생 · 결과만 확인

“보호 정보 없음 / 공개 예정 파일 / 제외 파일” 보고를 보고 이상이 없으면 Push를 승인합니다.

5
지니 · Commit & Push

승인된 범위만 GitHub Repository에 올리고 실제 원격 저장소를 다시 검증합니다.

02

학생이 꼭 알아야 하는 것은 “파일명”보다 “보호 대상”이다

WHAT MUST NEVER BE EXPOSED?

🔑 API Key / Token / Password

외부 서비스에 로그인하거나 비용이 발생하는 권한 정보입니다. 공개 Repository에 들어가면 안 됩니다.

🧾 .env / 환경설정 Secret

API Key나 비밀번호를 담는 경우가 많아 기본적으로 공개 여부를 반드시 검사해야 합니다.

👤 개인정보

실명, 이메일, 전화번호, 계정정보처럼 개인을 식별할 수 있는 정보는 공개하지 않습니다.

🖥️ Local 절대경로

C:\Users\...처럼 내 컴퓨터 구조와 사용자 이름이 드러나는 정보는 제거하거나 일반화합니다.

🤖 내부 Agent 협업 기록

BRIEF, STATE, Research 원본, QA 로그, Prompt 등은 공개 목적이 아니라면 Local에 보관합니다.

📦 불필요한 작업파일

임시파일, 실험용 Script, 대용량 산출물 등 App 실행에 필요하지 않은 파일은 공개 범위에서 제외할 수 있습니다.

학생에게 요구하지 않을 것: “index.html은 올리고 BRIEF.md는 빼고…”를 처음부터 외우게 하지 않습니다. 학생은 “비밀·개인정보·내부기록은 보호해야 한다”는 원칙만 이해하고, 실제 파일 분류는 토비의 지시를 받은 지니가 점검하도록 합니다.
03

명령어는 외우지 말고 “무슨 뜻인지”만 이해한다

LOCAL GIT · INIT → ADD → COMMIT

git init git branch -M main git status git add . git commit -m "feat: initial release"
명령쉬운 뜻
git init“이 폴더부터 Git으로 Version을 기록할게.”
git status“지금 무엇이 바뀌었는지 보여줘.”
git add .“이번 Version에 포함할 변경을 준비해.”
git commit“현재 상태에 이름표를 붙여 Version으로 기록해.”
main“현재 프로젝트의 공식 기준이 되는 대표 Branch.”
학생의 목표: 명령어를 암기하는 것이 아니라 “지니가 Version을 만들고 상태를 확인한 뒤 GitHub로 보낸다”는 흐름을 이해하면 충분합니다.

05

사람이 승인하면 처음으로 Push한다

HUMAN APPROVAL → PUSH

git remote -v git push -u origin main

“지니가 준비와 검사를 마치더라도,
GitHub로 실제 전송(Push)하는 마지막 승인은 학생이 한다.”

Push가 끝나면 지니가 원격 Repository(Internet의 GitHub 저장소)의 main을 다시 읽어 실제로 공개된 파일과 Secret 유출 여부를 확인합니다. 학생은 이 최종 보고를 보고 “GitHub 저장 완료”를 판단합니다.

06

Push 후에는 저장 상태를 확인하고, 원하면 GitHub에서도 바로 배포해 본다

POST-PUSH VERIFY → OPTIONAL GITHUB PAGES

Push가 끝났다면 먼저 “온라인 저장소에 제대로 들어갔는가?”를 확인합니다. 그다음 정적 Web App이라면 GitHub Pages(깃허브 페이지스: GitHub 저장소의 HTML/CSS/JS를 실제 Web URL로 보여주는 무료 정적 사이트 배포 기능)를 켜서 GitHub 자체에서도 바로 배포해 볼 수 있습니다.

  • 의도한 Repository의 main에 정상 Push되었는가?
  • Secret(비밀정보) / 개인정보 / .env가 공개되지 않았는가?
  • 내부 Agent 작업기록이 실수로 포함되지 않았는가?
  • README 등 공개 설명이 정상 보이는가?
  • Local(내 컴퓨터)의 최신 Commit과 GitHub의 최신 Commit이 같은가?
  • 추가로 Commit할 변경이 남아 있지 않은가?
GitHub Pages로도 배포할 수 있습니다.
GitHub Pages는 Repository의 정적 파일을 Web 사이트로 게시해 줍니다. 즉, GitHub는 저장·Version 관리가 중심이지만, 간단한 HTML/CSS/JavaScript App은 같은 GitHub 안에서 바로 Deploy(배포: Internet에서 URL로 접속할 수 있게 공개)할 수도 있습니다.

왜 같은 App이 두 주소에서 동시에 열릴까?

두 URL은 서로 다른 회사의 서로 다른 배포 공간입니다. 하나는 GitHub Pages, 다른 하나는 Google AI Studio입니다. 하지만 둘 다 같은 Source Code를 기준으로 배포했기 때문에 화면과 기능이 거의 똑같은 Web App처럼 보일 수 있습니다.

비유하면 같은 책을 두 도서관에 한 권씩 가져다 놓은 것과 비슷합니다. 책 내용은 같아도 도서관은 서로 다릅니다. 그래서 GitHub 쪽을 수정했다고 Google AI Studio 쪽이 자동으로 바뀌는 것은 아니며, 반대로 AI Studio에서 새로 Publish했다고 GitHub Pages가 자동으로 최신 상태가 되는 것도 아닙니다. 각각 최신 Source를 반영해 Deploy/Republish(배포/재배포)해야 합니다.

“같은 Web App인데 왜 GitHub Pages와 Google AI Studio라는 두 곳에 모두 배포할 수 있을까? 두 서비스는 무엇이 같고 무엇이 다를까?”

BEGINNER-SAFE GITHUB WORKFLOW

학생이 이해할 것

GitHub의 큰 역할

저장 + Version 관리(변경 이력을 차곡차곡 남기는 것)가 중심입니다. Commit(변경 상태 기록), Push(GitHub로 전송), Deploy/Publish(배포: Internet에서 실제 URL로 사용할 수 있게 공개)의 차이만 이해하면 됩니다.

학생이 승인할 것

Secret 보호와 외부 공개

API Key·Token·Password·개인정보·내부기록은 보호해야 한다는 원칙을 알고, 지니의 검사 결과를 확인한 뒤 Push를 승인합니다.

학생 → 토비: “GitHub에 올리려고 하는데 초보자인 내가 파일을 하나씩 판단하기는 어려워. 공개하면 안 되는 정보와 내부 작업파일을 지니가 검사하고 제외한 뒤, 공개에 필요한 최종 App 파일만 Commit/Push하도록 지시문을 만들어줘.”
A. 학생 승인 전 — 지니가 먼저 안전점검만 수행
[토비가 지니에게 만들어 주는 지시의 핵심 예시] GitHub Push 전에 Public Preflight(공개 전 안전점검)를 수행하세요. 1. API Key, Token, Password, .env, 개인정보, Local 절대경로를 검사하고 공개에서 제외하세요. 2. Agent 내부 작업기록, Research/QA 원본, 임시파일은 공개 목적이 아니면 제외하세요. 3. App 실행과 공개 설명에 필요한 파일만 Repository Root(저장소의 가장 바깥 시작 폴더)에 남기세요. 4. .gitignore(업로드 제외 목록)가 보호 대상 파일을 차단하는지 확인하세요. 5. 아직 Commit/Push하지 말고 아래만 먼저 보고하세요. - 공개 예정 파일 - 제외 파일 - Secret 검사 결과 - Repository 이름
⏸ 여기서 멈춤 — 학생 승인 학생이 지니의 안전점검 결과를 보고 “이대로 GitHub에 올려도 좋다”고 승인한 뒤에만 다음 단계로 진행합니다.
B. 학생 승인 후 — Commit & Push → 실제 GitHub 재검증
1. 승인된 공개 파일만 Commit(변경 상태 기록)하세요. 2. main Branch(대표 기준 줄기)에 Push(GitHub로 전송)하세요. 3. Push 후 실제 GitHub main을 다시 읽어 다음을 확인하세요. - 공개 파일이 승인된 목록과 같은가? - Secret/개인정보/내부 작업파일이 없는가? - 최신 Commit Hash(커밋 해시: 각 Commit을 구분하는 고유 번호)가 Local과 GitHub에서 같은가? 4. 최종 PASS/FAIL과 GitHub Repository URL을 학생에게 보고하세요.

“GitHub 수업의 목표는 명령어 암기가 아니다.
Version을 안전하게 남기고 → 보호할 것을 보호하고 → Push를 승인하고 → 필요하면 GitHub Pages로 배포까지 해 보며, 같은 App이 다른 Cloud에서도 실행될 수 있다는 궁금증을 갖는 것이다.”
