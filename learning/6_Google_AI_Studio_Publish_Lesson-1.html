GitHub에 저장한 App을
Google AI Studio로 실제 Web에 배포해 보자

이전 단계에서 GitHub에 최종 Source Code와 Version을 안전하게 저장했습니다. 이제 배포(Deploy/Publish), 즉 저장된 Code를 실제 Internet에서 실행해 다른 사람이 URL로 접속할 수 있게 만드는 단계로 넘어갑니다. 배포 방법은 GitHub Pages, Netlify, Vercel 등 다양하지만, 이번 수업에서는 Google AI Studio로 Import(가져오기) → Preview(미리 실행해 보기) → Publish(배포: Internet에서 접속할 수 있게 공개)하는 과정을 경험합니다.

이전 · GitHub 저장 / Version 확정 현재 · Google AI Studio Publish 배포 = 실제 URL로 공개 Preview 후 사람 승인 마지막 · 실제 스마트폰 Acceptance
00

배포(Deploy/Publish)는 무엇일까? — “창고의 상품을 실제 매장에 진열하는 것”

REPOSITORY ≠ DEPLOYED WEBSITE

GitHub에 Source Code(소스 코드: Web App을 만드는 원본 파일)를 저장한 것과 사람들이 실제 Web App을 사용하는 것은 서로 다른 단계입니다. 배포(Deploy/Publish)는 저장된 Code를 실제로 실행할 수 있는 Web 환경에 올려 공개 URL(Internet 주소)을 만드는 과정입니다.

GitHub Repository 완성된 파일과 Version 기록을 보관하는 창고
→
Deployment / Publish 사람들이 실제로 들어와 체험할 수 있는 매장과 주소(URL)를 만드는 것
GitHub에서도 직접 배포할 수 있습니다.
GitHub Pages는 정적 Web(서버에서 복잡한 계산을 하지 않고, 준비된 HTML·CSS·JavaScript 파일을 브라우저에 그대로 보여주는 비교적 단순한 Web 방식)을 URL로 공개할 수 있는 기능입니다. 즉 GitHub는 저장·Version 관리가 중심이지만, 간단한 Web App은 GitHub Pages를 이용해 바로 배포할 수도 있습니다.

그럼 왜 Google AI Studio도 사용할까?

Web App을 Internet에 공개하는 방법은 하나가 아닙니다. GitHub Pages, Google AI Studio, Netlify, Vercel 등 여러 서비스가 있고, 각각 지원하는 실행환경과 편의 기능이 조금씩 다릅니다. 이번 수업에서는 “같은 App을 다른 배포 공간에도 올릴 수 있다”는 것을 경험하기 위해 Google AI Studio를 사용합니다.

01

배포 방법은 여러 가지다 — 이번 수업은 Google AI Studio

MANY DEPLOYMENT OPTIONS · ONE LEARNING PATH

GITHUB
GitHub Pages

GitHub Repository의 정적 HTML/CSS/JS를 비교적 간단하게 Web URL로 공개할 수 있습니다.

GOOGLE
Google AI Studio

GitHub에서 App을 Import(가져오기)하고 Preview(미리 실행해 보기)한 뒤 Publish(배포: Internet에서 접속할 수 있게 공개)하여 AI Studio 공개 URL을 만드는 방법을 이번 수업에서 사용합니다.

HOSTING
Netlify

Web 프로젝트를 Git 저장소와 연결해 자동 Build·Deploy하는 데 널리 쓰이는 배포 서비스입니다.

HOSTING
Vercel

Frontend Web App을 Git 저장소와 연결해 배포하고 Version별 Preview를 관리할 수 있는 서비스입니다.

학생이 기억할 한 가지: “배포 방법에는 정답 하나만 있는 것이 아니다.” 이번 과정은 Google 생태계를 경험하는 수업이므로 Google AI Studio Publish를 선택합니다.

Preview가 정상이어야 Publish합니다.
Import 과정에서 AI Studio가 실행환경을 맞추기 위해 일부 설정 파일을 보완할 수 있습니다. 이때 App의 핵심 기능을 마음대로 바꾸는 것이 아니라 AI Studio에서 실행되기 위해 필요한 환경만 최소한으로 맞춘다고 이해하면 됩니다.
  • 첫 화면이 정상으로 보이는가?
  • 시작 버튼과 핵심 기능이 작동하는가?
  • 결과 화면이 정상 출력되는가?
  • PNG/PDF 같은 다운로드 기능이 필요한 경우 정상 작동하는가?
  • Preview(미리보기)가 정상인 것을 확인한 뒤 학생이 Publish(배포)를 승인했는가?
  • Publish 후 실제 공개 URL에서 다시 확인했는가?
03

왜 스마트폰에서도 확인할까? — 하나의 페이지가 여러 화면 크기에 맞아야 한다

RESPONSIVE WEB APP · ONE PAGE, MANY SCREEN SIZES

같은 Web App이라도 PC Browser(브라우저: Web 페이지를 보는 프로그램)와 스마트폰은 화면 크기가 크게 다릅니다. PC에서 두 칸으로 보기 좋은 화면을 스마트폰에서 그대로 보여주면 글자가 너무 작아지거나, 버튼과 Card가 서로 겹치거나, 옆으로 Scroll해야 하는 문제가 생길 수 있습니다.

그래서 “반응형 Web App”으로 만들어 달라고 합니다

반응형 Web App(Responsive Web App)은 같은 Web 페이지 하나가 PC·Tablet·Smartphone의 화면 폭에 맞춰 배치와 크기를 스스로 바꾸어 보여주는 방식입니다. PC용 페이지와 스마트폰용 페이지를 따로 만드는 것이 아니라, 한 페이지 안에 “넓을 때는 이렇게, 좁을 때는 이렇게”라는 여러 화면 규칙을 함께 넣어 두는 것입니다.

브라우저가 화면 폭을 안다예: 1440px, 430px, 390px
→
CSS의 화면 규칙을 선택넓은 화면 규칙 / 좁은 화면 규칙
→
같은 페이지를 다르게 배치2열 → 1열 · 버튼 폭 확대 · 글자 줄바꿈 조정

즉, 브라우저는 자신이 사용할 수 있는 화면 폭(Viewport, 뷰포트: Web 페이지가 실제로 보이는 영역)을 알고 있고, Web 페이지 안에 미리 작성된 CSS 규칙이 그 폭에 맞는 Layout(레이아웃: 화면 배치)을 선택합니다. 이것이 반응형 화면의 핵심입니다.

실제 스마트폰에서 발견할 수 있는 문제수정 방향
직업명 + 참고 배지 가로 충돌좁은 화면에서는 위·아래로 분리
긴 제목이 어색하게 줄바꿈됨한글 단어가 자연스럽게 묶이도록 조정
Card 안의 글을 읽을 공간이 좁음스마트폰에서는 좌우 여백을 줄여 본문 폭 확보
출처와 상세 링크가 한 줄에서 경쟁각각 별도 줄로 배치
하단 버튼이 작거나 나란히 있어 누르기 어려움버튼을 한 줄씩 넓게 배치

05

반응형 UI는 “작게 줄이기”가 아니라 화면 크기에 맞춰 다시 배치하는 것

RESPONSIVE UI = DIFFERENT LAYOUT RULES IN ONE PAGE

반응형 Web App은 모든 화면을 똑같이 축소해서 보여주는 것이 아닙니다. 같은 HTML 페이지 안에 여러 화면 크기에 맞는 CSS 규칙을 함께 적어 두고, 브라우저가 자신의 화면 폭을 기준으로 알맞은 규칙을 적용합니다.

한 페이지에 여러 화면용 규칙이 함께 들어 있습니다.
브라우저가 “지금 내가 보여줄 수 있는 폭이 얼마인지” 알고, Web 페이지의 CSS가 그 폭에 맞는 규칙을 골라 적용합니다. 그래서 PC와 스마트폰에서 서로 다른 App을 보는 것처럼 보여도 실제로는 같은 Web 페이지가 화면 크기에 맞춰 다른 Layout을 선택하고 있는 것입니다.
06

수정했는데 예전 화면이 보인다면 Browser Cache와 Republish를 확인한다

CACHE · REPUBLISH AWARENESS

Browser Cache(브라우저 캐시: 한 번 받아 본 이미지·CSS·JavaScript 같은 파일을 다음에 더 빨리 보여주기 위해 내 PC나 스마트폰에 잠시 저장해 두는 임시 저장공간) 때문에, 새 Version을 배포했는데도 잠시 예전 화면이 보일 수 있습니다.

Internet에는 새 Version이 있음

GitHub 또는 AI Studio에는 이미 수정된 파일이 배포되어 있습니다.

↔
내 Browser가 예전 파일을 기억하고 있음

속도를 높이려고 보관해 둔 Cache 때문에 이전 화면을 먼저 보여줄 수 있습니다.

또 하나의 경우 — GitHub만 수정하고 AI Studio는 다시 배포하지 않은 경우

GitHub Pages와 Google AI Studio는 서로 다른 배포 공간입니다. GitHub의 Source를 수정해도 AI Studio가 자동으로 최신 Version이 되는 것은 아닙니다. AI Studio에도 최신 Source를 다시 Import(가져오기)하고 Preview를 확인한 뒤 Republish(재배포: 수정된 Version을 다시 Internet에 공개)해야 합니다.

확인 순서:
① GitHub main에 최신 Version이 있는가? → ② Google AI Studio에 최신 Version을 Import(가져오기)했는가? → ③ Preview(미리보기)가 정상인가? → ④ 학생이 Publish/Republish(배포/재배포)를 승인했는가? → ⑤ 실제 URL에서 새로고침하거나 Browser Cache를 비운 뒤 다시 확인했는가?
