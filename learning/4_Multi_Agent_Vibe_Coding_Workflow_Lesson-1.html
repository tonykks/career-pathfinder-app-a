requirements.md 다음에는
AI들이 어떻게 협업할까?

학생이 Gemini와 대화해 requirements.md를 확정하면, 이제 구현은 지니(Antigravity IDE Agent)가 총괄합니다. 지니는 Terminal에서 애니(Antigravity CLI)와 토디(Codex CLI)를 명령으로 호출하고, 작업 지시와 실행 결과를 공유 파일(.md)에 남겨 문맥을 이어 갑니다. 학생은 마지막에 토비(생성형 AI · Gemini)와 지니 사이를 복사·붙여넣기로 연결해 “처음 의도와 실제 구현이 같은가?”를 검토합니다.

토비 · 생성형 AI (Gemini) 지니 · Antigravity IDE Agent 애니 · Antigravity CLI 토디 · Codex CLI 핵심 · Terminal + Markdown Handoff
00

전체 협업 흐름 — 학생은 방향을 정하고, AI 팀은 파일로 이어서 일한다

WHERE ARE WE NOW?

핵심은 “AI 여러 개를 동시에 켜 둔다”가 아닙니다. 지니가 총괄하고 → CLI 작업자에게 명령하고 → 결과를 파일로 받고 → 직접 검증하고 → 다시 수정시키는 반복 구조입니다. 파일에 지시와 결과를 남기기 때문에 CLI 실행이 끝나도 다음 작업에서 앞 문맥을 다시 읽어 이어갈 수 있습니다.

학생 ↔ 토비아이디어·의도 구체화
→

→

→

→

학생은 WHAT을 결정하고, 지니는 HOW를 총괄하며, 토디와 애니는 Terminal에서 실제 작업을 수행하고, .md 파일이 AI들 사이의 작업 기억과 전달문서가 됩니다.
01

먼저 이름부터 정확히 — 이 수업에서는 네 역할만 구분한다

FOUR CLEAR ROLES · NO TERMINOLOGY

TOBY · 생성형 AI

토비 = Gemini

학생과 대화하며 아이디어를 구체화하고, requirements.md를 만들도록 돕고, 마지막에는 지니의 구현 결과가 학생의 원래 의도를 충족하는지 검토합니다.

GENI · 총괄

지니 = Antigravity IDE Agent

requirements.md와 BRIEF.md를 읽고 전체 작업을 설계합니다. Terminal에서 애니·토디에게 명령을 내리고 결과 파일을 회수하며, 수정된 파일과 Test 결과를 직접 확인해 다시 보완시킵니다.

ANNY · 독립 검토

애니 = Antigravity CLI

Terminal에서 호출되는 독립 CLI 작업자입니다. 지니가 지정한 파일과 구현 결과를 읽고, 요구사항 누락·오류·Regression을 검토하고 Test한 뒤 결과를 .md 파일에 기록합니다.

TODY · 구현

토디 = Codex CLI

Terminal에서 호출되는 Coding 작업자입니다. 지니의 작업 지시 파일을 읽고 코드를 구현·수정하며, 무엇을 바꿨고 어떤 Test를 했는지 결과 파일에 기록합니다.

이번 자료에서는 네 역할만 구분합니다.
학생은 복잡한 Agent 계층을 외울 필요 없이 토비(대화·의도) / 지니(총괄) / 토디(Coding) / 애니(독립 검토·Test) 네 역할만 이해하면 됩니다.
02

BRIEF PASS가 출발 신호 — 그다음 Terminal과 파일로 협업한다

BRIEF APPROVAL → TERMINAL COMMAND → TASK FILE → RESULT FILE

지니가 requirements.md를 읽고 Deep Research를 수행해 “어떻게 구현할 것인가(HOW)”를 BRIEF.md로 정리하면, 학생은 그 내용을 토비에게 전달해 원래 요구사항을 빠짐없이 충족하는지 검토받습니다. 토비의 피드백을 다시 지니에게 전달하고, 토비가 PASS할 때까지 지니가 BRIEF.md를 수정합니다. 이 승인 전에는 본격 Coding으로 넘어가지 않는 것이 이 수업의 원칙입니다.

requirements.md학생이 정한 WHAT
→
지니 Research근거·사례·구현 방법 조사
→
BRIEF.md지니가 정리한 HOW
↔
토비 검토 · 지니 수정요구사항 충족까지 반복
→
PASS이제 CLI 작업 시작
환경 준비는 이렇게 이해하면 충분합니다.
이 수업에서는 Terminal에 Codex CLI(토디)와 Antigravity CLI(애니)가 설치·로그인되어 있다고 가정합니다. 학생이 설치 명령을 모두 외우는 것이 목표가 아니라, 지니가 Terminal 명령으로 두 CLI 작업자를 호출한다는 구조를 이해하는 것이 목표입니다.

애니와 토디는 IDE 안의 채팅창에서 계속 대화하는 방식이 아니라, 컴퓨터의 Terminal에 설치된 CLI를 지니가 명령어로 실행하는 방식으로 사용합니다. 한 번의 CLI 실행이 끝난 뒤에도 앞의 작업 문맥을 잃지 않도록, 지니는 지시사항을 Markdown 파일에 쓰고 CLI는 실행 결과를 다시 Markdown 파일에 남깁니다.

① 지니 → 토디

Coding 작업 지시

예: 지니가 tody-task.md에 수정 대상, 완료조건, 금지사항을 기록한 뒤 Terminal에서 codex exec ... 형태로 토디에게 그 파일을 읽고 작업하도록 지시합니다.

② 토디 → 지니

구현 결과 기록

토디는 코드를 수정한 뒤 tody-result.md에 변경 파일, 구현 내용, 실행한 Test, 남은 문제를 기록합니다. 지니는 이 파일을 읽고 실제 변경 파일도 직접 확인합니다.

③ 지니 → 애니

독립 Review · Test 지시

지니가 any-task.md에 검토 범위와 PASS 기준을 적고, Terminal에서 agy --print ... 같은 명령으로 애니에게 독립 검증을 요청합니다.

④ 애니 → 지니

QA 결과 기록

애니는 요구사항 누락, 오류, Regression, Test 결과를 any-result.md에 남깁니다. FAIL이면 지니가 다시 토디에게 수정 지시를 만들고 같은 Loop를 반복합니다.

왜 굳이 파일에 남길까?
CLI를 여러 번 독립 실행하면 매번 이전 대화 전체를 자동으로 기억한다고 가정할 수 없습니다. 그래서 작업 지시와 실행 결과를 파일로 남겨 “공유 기억”처럼 사용합니다. 다음 AI는 그 파일을 읽고 앞 작업의 문맥을 이어서 일할 수 있고, 사람도 나중에 무엇을 지시했고 무엇이 바뀌었는지 확인할 수 있습니다.
※ 위 파일명과 명령 형식은 수업 이해를 위한 예시이며 프로젝트 환경에 따라 달라질 수 있습니다.
03

Coding과 검토는 이렇게 반복된다 — 토디가 만들고, 애니가 따로 확인한다

IMPLEMENT → REVIEW → FIX LOOP

토디가 한 번 코딩했다고 끝나는 것이 아닙니다. 토디 구현 → 애니 독립 검토·Test → 지니 확인 → 수정 지시 → 다시 구현·검토를 반복해 요구사항과 완료조건을 모두 만족할 때까지 품질을 높입니다.

지니작업 지시 파일 작성
→
토디Coding · 수정 · 결과 기록
→
애니독립 Review · Test · 결과 기록
→
지니결과 파일 + 실제 코드 확인
↺
FAIL이면 반복수정 지시 → 재구현 → 재검증
역할남기는 기록다음 작업자가 확인하는 것
지니작업 목적 · 수정 범위 · 완료조건 · 금지사항토디와 애니가 무엇을 해야 하는지
토디변경 파일 · Coding 내용 · Test 결과 · 남은 문제지니가 실제 구현이 지시와 맞는지
애니PASS/FAIL · 발견 오류 · 누락 요구사항 · Regression 결과지니가 어떤 보완이 필요한지
04

지니는 결과 보고만 믿지 않는다 — 수정된 파일을 직접 다시 확인한다

ORCHESTRATOR VERIFICATION

토디가 “완료했습니다”, 애니가 “PASS입니다”라고 기록했다고 해서 지니가 그대로 끝내는 것은 아닙니다. 지니는 결과 파일을 읽고, 실제로 수정된 파일을 하나씩 열어 변경 내용을 확인하고, Test 결과와 실행 화면이 요구사항을 만족하는지 다시 검증합니다.

CHECK 1

결과 파일과 실제 Code가 같은가?

토디가 기록한 변경 파일 목록과 실제 diff를 비교하고, 요청하지 않은 범위까지 바뀌지는 않았는지 확인합니다.

CHECK 2

Test가 정말 완료조건을 검증했는가?

애니의 PASS 문구만 보는 것이 아니라 어떤 Test를 했고, 요구사항의 핵심 기능과 기존 기능 Regression까지 확인했는지 살펴봅니다.

지니의 역할은 “전달자”가 아니라 총괄 검증자입니다.
부족한 점이 발견되면 지니가 새 수정 지시 파일을 만들고 토디·애니에게 다시 작업시킵니다. 이 과정을 거쳐 “CLI 작업 완료”가 아니라 “지니 검증 완료” 상태가 되어야 다음 단계로 넘어갑니다.
05

마지막에는 다시 토비가 검토한다 — 학생이 토비와 지니를 연결한다

STUDENT AS THE HUMAN BRIDGE

지니가 기술적으로 구현과 Test를 완료해도 마지막 질문이 남습니다. “이 결과가 처음 학생이 만들고 싶었던 것과 같은가?”입니다. 이 검토는 학생과 처음부터 의도를 구체화했던 토비가 맡습니다. 현재 수업에서는 토비와 지니가 자동으로 직접 대화하는 것이 아니라, 학생이 필요한 내용을 복사·붙여넣기하여 둘을 연결합니다.

학생 → 지니
지금까지 구현·검토한 결과를 정리해서 토비가 검토할 수 있는 완료 보고로 만들어 주세요.
지니
구현 파일, Test 결과, 남은 이슈와 요구사항 충족 여부를 정리해 완료 보고 파일에 기록했습니다.
학생 → 토비
지니의 완료 보고를 복사해 왔어요. 처음 확정한 requirements.md와 비교해서 의도가 정확히 구현되었는지 검토해 주세요.
토비
요구사항과 비교해 누락·과도한 구현·수정 필요사항을 정리합니다. 모두 충족하면 PASS를 알립니다.
학생 → 지니
토비의 피드백을 그대로 전달할게요. 필요한 부분만 수정하고 다시 검증해 주세요.

학생의 복사·붙여넣기는 단순 전달 작업이 아니라,
“의도 검토 AI(토비)”와 “개발 총괄 AI(지니)”를 연결하는 Human-in-the-loop 역할입니다.

06

학생은 어디에서 개입할까? — 중요한 지점만 복사·붙여넣기로 연결한다

HUMAN-IN-THE-LOOP CHECKPOINTS

시점학생이 하는 일AI가 하는 일
① 요구사항토비와 대화하며 만들고 싶은 것을 확정한다.토비가 requirements.md로 정리한다.
② 구현 설계지니의 BRIEF.md를 토비에게 전달해 검토받고 피드백을 다시 지니에게 전달한다.지니가 Research와 BRIEF를 수정해 HOW를 확정한다.
③ 개발 중저수준 Coding 과정에는 매번 개입하지 않고 중요한 변경만 확인한다.지니가 Terminal로 토디·애니를 호출해 구현·검토·Test를 반복한다.
④ 완료 검토지니의 완료 보고를 토비에게 전달하고 피드백을 다시 지니에게 전달한다.토비가 의도를 검토하고 지니가 필요한 수정을 반영한다.
⑤ 최종 판단학생이 직접 실행해 “내가 원한 결과인가?”를 판단한다.PASS된 결과를 배포할 준비를 한다.
중요: 학생은 모든 Terminal 명령과 Code를 이해할 필요가 없습니다. 대신 “누가 무엇을 맡고, 어떤 파일로 결과를 전달하며, 언제 내가 판단해야 하는가”를 이해하면 됩니다. 첫 번째 Vibe Coding 입문에서는 이 역할 분담을 목표로 정하고, 같은 Workflow를 여러 번 반복해 자연스럽게 체화하는 것이 중요합니다.

최종 Workflow — 말로 시작한 아이디어가 파일과 검증 Loop를 거쳐 App이 된다

→

학생 실행최종 확인 · 배포 판단
  • 토비: 학생의 의도와 최종 결과가 일치하는지 지킨다.
  • 지니: 전체 개발을 계획하고 CLI 작업을 지휘하며 실제 파일과 Test 결과를 직접 검증한다.
  • 토디: 지시 파일을 읽고 Coding·수정한 뒤 결과를 파일에 남긴다.
  • 애니: 독립적으로 검토·Test하고 PASS/FAIL과 근거를 파일에 남긴다.
  • 학생: 토비와 요구사항을 확정하고, 지니와 토비 사이의 통로가 되며, 마지막 결과가 자신의 목적과 같은지 직접 실행해 최종 판단한다.
왜 “최종 검수 40%”가 중요한가? — 실제 App A 사례
App A에는 직업 Data가 15개 있었고 자동 Test도 통과했지만, 학생이 실제로 여러 번 실행해 보니 비슷한 직업만 반복해서 나오는 이상함이 발견되었습니다. 확인 결과 같은 진로 Domain에서 사실상 첫 번째 직업만 선택되는 구조여서 15개 Data가 있어도 실제 결과 후보는 훨씬 적었습니다. 이 문제는 학생의 반복 사용 → 토비 검토 → 지니 수정 → 토디 구현 → 애니 재Test를 거쳐 모든 직업이 실제 결과로 도달 가능한지 다시 검증하는 방식으로 보완했습니다.

즉, 자동 QA가 PASS해도 “내가 직접 써 보니 이상하다”는 학생의 감각이 마지막 품질검사의 중요한 Sensor가 될 수 있습니다.

지니의 역할은 “코딩하는 사람”보다 “AI 개발팀장”에 가깝다

학생이 HOW를 직접 알지 못해도 지니가 아래 과정을 총괄합니다.

토비 ↔ 지니 연결 역할

BRIEF 검토와 완료 검토에서 필요한 내용을 복사·붙여넣기로 전달해 두 AI가 같은 의도를 유지하도록 연결합니다.

“Vibe Coding 첫걸음에서 학생의 핵심 역할은 Coding이 아닙니다.
학생 ↔ 토비로 요구사항을 확정하고(50%) → 토비 ↔ 학생으로 결과를 검수·완성하며(40%) → 지니 ↔ 학생 ↔ 토비의 통로가 되는 것(10%)입니다.”

이 세 가지 역할을 이해하면 Vibe Coding의 첫걸음은 이미 성공적으로 시작된 것입니다.

첫 입문 단계에서는 컴퓨터의 Agent가 작성하는 Code를 전혀 이해하지 못해도 시작할 수 있습니다. 학생은 먼저 “내가 무엇을 만들고 싶은가?”와 “완성된 결과가 내가 원했던 것인가?”에 집중하면 됩니다. Coding과 Test의 세부 기술은 지니·토디·애니에게 맡기고, 작은 Web App을 여러 번 만들어 같은 Workflow를 반복하면서 자연스럽게 익혀 갑니다. 기술을 다 알아야 시작하는 것이 아니라, 먼저 만들어 보면서 새로운 도전을 계속할 수 있다는 자신감을 얻는 것이 이 첫 수업의 목표입니다.

첫 번째 Vibe Coding 입문의 학습 목표:
이 50% · 40% · 10% 역할 분담은 절대적인 수치가 아니라 초보자가 무엇에 집중해야 하는지 보여주는 교육용 기준입니다. 처음에는 이 Workflow를 명확한 목표로 잡고, 작은 Web App을 여러 번 만들어 보면서 같은 과정을 반복해 몸에 익히는 것이 중요합니다. 처음부터 CLI 설치법, Agent 내부 구조, 모든 Test 명령이나 Code를 세세하게 이해하려고 부담을 가질 필요는 없습니다. WHAT을 내가 결정하고 → HOW는 지니에게 맡기고 → 파일로 협업시키고 → 내가 최종 검수한다는 큰 흐름을 먼저 체화합니다. 작은 성공을 반복할수록 학생은 “내가 결정해야 할 것”과 “AI에게 맡겨도 되는 것”을 자연스럽게 구분하고, 다음에는 조금 더 어려운 App에도 도전할 마음을 갖게 됩니다.
