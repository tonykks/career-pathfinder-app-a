04

실패 사례 2 — Desktop과 PNG는 좋은데 스마트폰 Web은 어색했다

PRODUCT QUALITY IS CONTEXTUAL

같은 App이라도 Desktop Web / Smartphone Web / PNG Report / PDF Report는 서로 다른 사용환경입니다. 하나가 잘 보인다고 나머지도 자동으로 좋은 것은 아닙니다.

정상

PNG/PDF

고정된 Report Layout이어서 인쇄형 결과물이 매우 안정적으로 보였습니다.

추가 수정 필요

Smartphone Web

직업명·Badge·Link·Button의 공간 배치를 다시 설계해야 했습니다.

교훈: 수정 범위를 정확히 제한해 모바일 Web만 고치고 출력물은 보호했습니다.

06

“완성”은 한 번의 PASS가 아니라 여러 Gate를 모두 통과한 상태다

DEFINITION OF DONE

GATE 1
Intent

처음 만들고 싶었던 App과 방향이 같은가?

GATE 2
Evidence

Research와 구현 가정이 구분되어 있는가?

GATE 3
Functional QA

기능·Algorithm·Export가 Test를 통과했는가?

GATE 4
Human Acceptance

사람이 실제로 사용했을 때 결과가 자연스러운가?

GATE 5
Publication Safety

외부에 공개해도 되는 파일만 Push했는가?

GATE 6
Real Device

실제 스마트폰과 Web URL에서도 잘 동작하는가?

07

왜 App A를 이제 동결하고 App B를 만들어야 할까?

BASELINE FOR COMPARISON

App A의 목적은 “Gemini와 학생이 만든 요구사항을 구현하면 실제로 어떤 결과가 나오는가?”를 경험하는 것이었습니다. 계속 개선하면 비교 기준이 움직입니다.

APP A

학생 + Gemini 요구사항

실제 대화로 만든 요구사항을 지니팀이 구현한 결과. 이번 수업의 Baseline입니다.

APP B

Research 기반 재설계

처음부터 더 명확한 진로 탐색 원리와 질문·Scoring·결과 표현을 설계하여 다시 구현합니다.

같은 아이디어라도
요구사항의 질과 Research의 사용법에 따라 결과는 달라진다.
