01

Geni-Research — Antigravity 안의 조사 전문 Subagent

GOOGLE ANTIGRAVITY SUBAGENT · RESEARCH

Geni-Research는 별도 제품을 추가 설치하는 개념이 아니라, Google Antigravity IDE 안에서 지니가 조사 과제를 분리해 맡기는 전문 Agent 역할입니다. 공식 자료 조사, 근거 수집, 비교표 작성처럼 구현 전에 확인해야 할 작업을 맡깁니다.

주요 역할

Research

공식 진로 자료와 요구사항의 근거를 조사하고 Markdown 결과로 남깁니다.

지니와의 관계

Task 단위 위임

지니가 범위·완료조건을 정해 과제를 배정하고 결과를 다시 회수·통합합니다.

학생용 한 문장: Geni-Research는 지니가 필요할 때 불러 쓰는 Google 쪽 조사 전문 팀원입니다.
02

Geni-Dev — Antigravity 안의 구현 전문 Subagent

GOOGLE ANTIGRAVITY SUBAGENT · BUILD

Geni-Dev는 지니가 HTML/CSS/JavaScript 구현, 계산 Logic, UI 수정 같은 개발 과제를 분리해 맡기는 Antigravity Subagent 역할입니다. 학생은 코드를 직접 작성하기보다 지니가 나눈 Task와 결과를 확인합니다.

STEP 1
지니가 BRIEF 확인

승인된 요구사항과 성공 기준을 읽습니다.

STEP 2
구현 Task 분리

화면, Scoring, Data, Export, Responsive UI처럼 기능 단위로 나눕니다.

STEP 3
Geni-Dev에 배정

필요한 파일과 완료 조건을 함께 전달합니다.

STEP 4
지니가 결과 회수·통합

Source Code와 Test 결과를 읽고 전체 App에 반영합니다.

지니 → Antigravity Task "구현 과제" ↓ Geni-Dev ↓ Source Code / Markdown 결과 ↓ 지니 통합
03

애니 연결 준비 — Google Antigravity CLI 설치

ANTIGRAVITY IDE ↔ ANTIGRAVITY CLI

Antigravity CLI는 Antigravity Agent를 Terminal에서 호출하는 가벼운 TUI/CLI입니다. Multi-step reasoning, 여러 파일 편집, Tool 호출, Subagent 등을 사용할 수 있고 우리 협업 Kit에서는 이 통로로 호출되는 전문 Agent를 애니(Any)라고 부릅니다.

STEP 1
Windows PowerShell 열기

설치 명령은 일반 PowerShell에서 실행할 수 있습니다.

STEP 2
Antigravity CLI 설치

Google 공식 Windows 설치 명령은 다음과 같습니다.

irm https://antigravity.google/cli/install.ps1 | iex
STEP 3
새 Terminal에서 실행

설치 후 새 Terminal을 열어 Project 폴더로 이동한 뒤 실행합니다.

agy
STEP 4
첫 실행 설정·로그인

처음에는 화면 Theme, Rendering 방식, Workspace Trust를 확인하고, 저장된 인증이 없으면 Browser가 열려 Google 계정 로그인을 진행합니다.

STEP 5
지니가 애니를 호출할 통로 확보

협업 Kit에서는 지니가 agy --print 등의 비대화형 호출을 사용해 검토·Research 과제를 맡기고 stdout 결과를 파일로 저장해 다시 읽는 구조를 사용합니다.

예시 개념 지니 → agy --print "Geni-Research의 출처를 독립적으로 Cross-check해" 애니 → 검토 결과 출력 지니 → 결과를 verification / review 파일로 저장·회수
학생용 한 문장: Antigravity CLI를 설치한다는 것은 “지니가 Google 쪽 전문 Reviewer/개발자에게도 Terminal로 일을 맡길 두 번째 전화선을 연결한다”는 뜻입니다.

4차 작업 — Research가 끝난 뒤에만 Coding을 배정한다

IMPLEMENTATION DELEGATION

지니 · 작업 분해

① 구현을 기능 단위로 나눈다

예: 화면 구조, 별점 입력, Scoring Engine, 직업 Data, PNG/PDF Export, Responsive CSS 등으로 나눕니다.

지니 · 배정

② 가장 적합한 Agent에게 나눈다

Geni-Dev에게 계산·구현과 UI/CSS를 맡기고, 필요하면 다른 Antigravity Subagent에 병렬 Task를 배정할 수 있습니다. 역할은 고정이 아니라 지니가 BRIEF와 자원 상황을 보고 결정합니다.

구현 Agent

③ 실제 Source Code 생성·수정

현재 사례처럼 index.html, style.css, app.js, data.js 같은 실제 App 파일이 생깁니다.

지니 · 통합

④ 서로 다른 Agent 결과를 한 App으로 합친다

파일 충돌을 확인하고 기능을 연결합니다. 필요하면 직접 수정하고 Local Server를 실행하여 App이 열리는지 확인합니다.

실제 수정 사례 — “직업 15개를 넣었는데 왜 6개만 나올까?”

REAL BUG → HUMAN DISCOVERY → ALGORITHM REVISION → REACHABILITY QA

1차 App은 기술적으로 정상 작동했고 PDF도 만들어졌습니다. 하지만 사람이 여러 번 직접 사용해 보니 입력 점수를 바꿔도 비슷한 직업만 반복해서 등장했습니다. Code를 다시 검토한 결과, 15개의 직업 Data가 있어도 각 Domain의 첫 번째 직업만 선택하는 구조라 실제 결과 후보는 약 6개뿐이라는 문제가 발견되었습니다.

학생 직접 Test“왜 계속 비슷한 직업만 나오지?”
→
토비 Code ReviewJOBS_DATASET.find() 구조 확인
→
원인 발견Domain마다 첫 번째 직업만 고정 선택
→
지니 수정 계획직업별 subjectAffinity 도입
→
Reachability QA15개 직업이 실제 결과로 모두 도달 가능한지 검증
기존 방식

Top Domain → 첫 번째 직업

예를 들어 인문사회가 1위가 되면 입력 Profile이 달라도 항상 Dataset의 첫 번째 대표 직업이 선택될 수 있었습니다.

수정 방식

Top Domain → 직업별 세부 점수

Domain 순위는 기존대로 유지하되, 같은 Domain 안에서는 각 직업의 subjectAffinity와 학생의 교과목 선호도를 이용해 세부 점수를 계산하여 가장 높은 직업을 고릅니다.

1
Geni-Research · 직업별 Affinity Data 조사·초안 작성

직업 15개 각각에 어떤 과목 조합이 상대적으로 더 연결될지 Research 결과를 참고하여 Data를 작성합니다. 직접적인 공식 Mapping이 아니라면 반드시 [App A 구현 가정]으로 기록합니다.

2
지니 · data.js에 subjectAffinity 반영

IDE가 실수로 종료되기 전 실제로 여기까지 완료되었고, 재시작 후 기록을 읽어 이 지점부터 작업을 이어가도록 했습니다.

3
지니/구현 Agent · app.js calculateTopJobs() 수정

각 Top Domain 내부 후보 직업들의 세부 점수를 계산하여 직업을 선택하도록 Algorithm을 수정합니다.

4
15개 직업 Reachability Test

“Dataset에 존재한다”가 아니라, 실제 입력 Profile을 만들었을 때 15개 직업 각각이 결과로 한 번 이상 나올 수 있는지 자동/수동 Test Case로 검증합니다.

5
애니 · 새 Mapping과 Algorithm 독립 Cross-check & QA

같은 입력은 항상 같은 결과인지, 같은 Domain에서도 입력에 따라 다른 직업이 나오는지, 기존 Domain Scoring과 Export 기능이 깨지지 않았는지를 다시 확인합니다.

6
애니 최종 QA → PASS

15/15 직업 Reachability 100%, 같은 Domain 내 동적 직업 선택, No Random 결정론성, 기존 6개 Domain Score 보존, 추천 이유 과목 Binding, FR/NFR 및 PNG/PDF 기능까지 PASS했습니다.

7
지니 · DECISIONS / VERIFICATION / STATE 최종 갱신

2-Tier Algorithm과 [App A 구현 가정], Reachability 및 Any QA PASS를 기록하고 GitHub Push 없이 멈췄습니다.

이 사례가 중요한 이유:
Agent들의 자동 QA가 끝났어도 사람이 실제로 여러 번 사용하면서 “결과가 이상하게 반복된다”는 느낌을 발견할 수 있습니다. Vibe Coding에서 Human Acceptance는 단순한 형식적 승인 단계가 아니라, 자동 Test가 놓친 Product 문제를 발견하는 마지막 Sensor입니다.
15

최종 QA가 끝나면 — 학생이 직접 실행해서 Acceptance Test

LOCAL SERVER → HUMAN ACCEPTANCE

지금 App A는 자동 Test 기준으로 최종 PASS했습니다. 하지만 GitHub에 올리기 전에 학생이 직접 Browser에서 여러 입력 Profile을 넣어 결과 다양성·사용성·PDF Export를 다시 확인합니다.

“취합”의 의미: 여러 AI의 결과를 단순히 한 폴더에 모으는 것이 아닙니다. 지니가 충돌을 해결하고, 최종 Code와 최종 판단 기준을 하나로 맞추며, 검증 증거까지 정리하는 것입니다.

마지막 — AI 개발팀이 PASS해도 학생과 토비가 다시 본다

HUMAN ACCEPTANCE

지니·Geni-Dev·애니가 할 수 있는 것은 “requirements대로 기술적으로 잘 만들었는가?”까지입니다. 하지만 “이 requirements 자체가 처음 내가 원한 App인가?”는 학생이 판단해야 합니다. 그래서 마지막에 학생이 App을 직접 실행하고 토비와 결과를 비교합니다.

완성 / 수정사람이 최종 결정

  • 근거: 진로정보의 근거와 구현 가정이 구분되어 있는가?
  • 사용성: 실제 학생이 쓰기 쉬운가?
  • 의도: 처음 내가 만들고 싶었던 App과 같은가?
  • 다르면: requirements를 수정하고 다시 Agent Loop로 보낼 것인가?
